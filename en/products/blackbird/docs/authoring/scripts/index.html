Develop and debug Action scripts

Build scripts that handle tools, results, and failures clearly.

Based on 0.8.3-alpha.4 development documentation. Updated 2026-09-22. Some features may differ from your installed version.

Use the generated starter

Choose an execution runner deliberately. Shipped Windows PowerShell Actions target Windows PowerShell 5.1. Selecting pwsh requires PowerShell 7 to be available; Bash needs an available compatible runner. A platform entrypoint does not make unsupported app platforms supported.

Keep the runtime import and unhandled-failure trap in PowerShell. Implement one small read-only operation first, run it through Blackbird, and inspect its result before adding writes or external effects. The Execution page can provide runner-specific instructions and a script preview; review generated or AI-assisted code before running it.

Call tools safely

Use the tool's executable and separate argument values. Do not concatenate an untrusted path/value into a shell command. Resolve package files relative to the package root and user files through declared inputs. Check existence and domain requirements before writing anything.

For PowerShell native commands, use the available runtime native-command helper where appropriate, or explicitly check the native exit code. PowerShell does not turn every nonzero native exit into a terminating exception. Standard error can contain informational output; the exit contract and recognized provider diagnostics matter.

Report progress and completion

Write-BlackbirdProgress -Label 'Inspecting files' -Value 50 -Detail '5 of 10 files'
Set-BlackbirdSuccessResult -Title 'Inspection complete' -Message 'All selected files were checked.'

Use an actual count/percentage when known. Otherwise use -Indeterminate. Write concise diagnostic messages without echoing secrets. Action execution already has a log entry; do not fabricate extra runs to represent progress.

For a known failure, publish a concrete correction and terminate unsuccessfully: ``powershell Set-BlackbirdFailureResult -Title 'Input missing' -Message 'The selected build file does not exist.' -Guidance 'Choose an existing build file and run again.' throw 'Selected build file does not exist.' `` The fallback trap preserves a specialized failure result. For a conditionally required persistent setting, use its canonical Get-BlackbirdParameter -Required path so Blackbird can offer Configure Setting.

Test before sharing

Test the happy path, missing/invalid inputs, tool failure, cancellation, and paths containing spaces. Stop requests cancellation; it does not automatically undo external writes. Keep destructive operations explicitly confirmed and preserve unrelated files. Use recoverable deletion for user-owned data rather than silently deleting it permanently.

Reload after script edits and validate manifest edits through the Action editor. If a script works only in your terminal, compare runner version, working directory, environment, credentials, and the supplied Blackbird context.
