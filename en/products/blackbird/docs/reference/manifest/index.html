Package manifest reference

Understand the file connecting a package to its scripts and dependencies.

Based on 0.8.3-alpha.4 development documentation. Updated 2026-09-22. Some features may differ from your installed version.

Package identity

Every package has package.json and its local script/module files. Its stable ID uses lowercase kebab-case and matches its directory. Types are action, library, and discovery. A bundle is a collection of packages; it is not another spelling of Action.

Action behavior

The action object declares requiresProject, requiresDevice, supportedDeviceKinds, dangerLevel, confirmBeforeRun, and related UI/execution behavior. Declare actual requirements rather than checking an arbitrary current device inside a supposedly device-independent Action.

Use a destructive danger level and confirmation for consequential writes/deletions/publication. A confirmation is not rollback. Success/failure results use completion dialogs; do not implement a separate result-toast mechanism.

Entrypoints and dependencies

An Action entrypoint selects a platform, runner, and file path or inline command. Supported runner names include process, powershell, pwsh, and bash. Availability of an entrypoint does not install its runtime. File paths and working directories must stay within the package; use user inputs for external data paths.

Libraries expose runner-compatible module entrypoints. Required dependencies must be libraries, exist, and have no cycles. Every declared required/optional library interface must reflect tested compatibility; version ordering is not evidence of an interface.

Edit and validate

Prefer Edit Action for manifest changes. Validate the package, run it through Blackbird, and test failure cases before sharing. Use the complete downloadable tutorial example as a starting point instead of treating a JSON fragment from a reference table as a full manifest.
