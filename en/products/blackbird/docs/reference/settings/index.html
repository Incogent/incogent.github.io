Setting definition reference

Look up the fields that describe an Action input.

Based on Blackbird 0.8.4-alpha.1. Updated 2026-10-08. Some features may differ from your installed version.

Shared definitions

Definitions live in explicitly listed JSON files owned by shared libraries. An Action references each through settings.inputs using owner, definition, and exact revision; it must depend directly on the owning library. Matching labels do not share settings.

Definition fieldMeaning
id / revisionStable namespace.key identity and value-contract revision
label / descriptionFriendly name and field help, including Markdown links
typetext, integer, number, boolean, choice, file, folder, secret, or array
scopeproject, application, or run
defaultFallback value; prohibited for secrets
rememberRunValueWhether a non-secret run suggestion may be retained
category / container / orderAuthored display placement
valueModesingle or supported project namedOptions
choices / allowCustomChoiceStatic choices and optional custom entry
itemFields / itemLabelArray record fields and item label

Action usages

Requiredness, profile membership, visibleWhen, and enabledWhen belong to each Action input usage. Conditions reference parameterId and values, with optional and conditions. For arrays, itemField selects a declared record field; followItemOrder on a visibility condition lets run fields follow the configured item order.

Declare profiles in settings.profiles with their label and display placement. Definitions own their categories and containers; advanced containers use presentation: advanced and may have a parent in the same category. Project sections precede Build profiles, controlling fields precede dependent choices, and advanced fields come last. Category dropdowns sort alphabetically.

Dynamic choices

Choice-provider scripts live in the definition owner's package. Use an owner-relative path and emit only a JSON string array on standard output. Keep diagnostic text separate. Providers run when choices are requested, not while merely reading definitions.

Revisions and values

Display-only edits retain the definition revision. Value-contract edits require a new revision and coordinated consumer references. The editor reviews affected Actions in the editable bundle before saving. Other bundles' definitions cannot be changed implicitly.

Stored project values and Queue/Workflow snapshots remain separate from definitions. Review saved runs after incompatible changes; new defaults do not repair old values automatically.
